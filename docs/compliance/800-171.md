# SP 800-171 evidence map

This maps cui-guard features and project practices to NIST requirements as evidence. It does not certify, assess or authorize anything.

Catalogs: SP 800-171 Rev 2 (Update 1) IDs lead, and Rev 3 (final, 2024-05-14) IDs sit alongside. IDs and Rev 3 titles were checked against NIST's published catalogs on 2026-10-29; see `docs/compliance/README.md` for the sources. Rev 2 has no requirement titles, so the Title column is the Rev 3 title.

Why Rev 2 leads: DFARS 252.204-7012 and CMMC Level 2 use Rev 2 under class deviation 2024-O0013, as of 2026-07-20. The CMMC Phase 2 suspension of 2026-07-13 is recorded as of 2026-10-29 in `docs/compliance/README.md`. These notes go stale, so check the primary sources before relying on them.

cui-guard is one control in front of one data path: the requests an AI agent sends to an LLM endpoint. It does not make a system meet any requirement on its own. Detection is heuristic, so read `docs/LIMITS.md` first. The SSP statements below describe a configuration. The customer edits them for their own system.

| 3.1.3 | 03.01.03 | Information Flow Enforcement | Inspects every outbound request (body, headers and query) and blocks or pseudonymizes what the policy forbids. Classified markings and unparseable content are always blocked. Placeholders are withheld from tool calls that name an outside host. Redirects are refused. Evidence: `src/cui_guard/pipeline.py`, `src/cui_guard/detect/`, `src/cui_guard/pseudo/egress.py`, `src/cui_guard/policy/`, `src/cui_guard/gateway/app.py`, `tests/leak/`, `tests/pentest/`, `tests/redteam/`, `tests/fuzz/` | An organization policy that defines CUI identifiers, lanes and the strictest settings. Agents pointed at the gateway. Loosening a default needs OS authentication through `src/cui_guard/override/`. | Defining what counts as CUI. Keeping agents from reaching the provider by a route that skips the gateway (see `docs/LIMITS.md`). Reviewing residual risk from heuristic detection. | The organization deploys cui-guard with an organization policy that lists its CUI identifiers and sets the strictest egress settings, and routes AI agent traffic through the local gateway. The gateway blocks or pseudonymizes policy-forbidden content before a request leaves the host. |
| 3.3.1 | 03.03.01 | Event Logging | Writes one audit record per decision. The log is append-only and never holds matched values. Evidence: `src/cui_guard/audit.py`, `tests/leak/` | Audit logging enabled in policy, with a log path on storage the organization manages. | Retention, forwarding to a central log store, review and analysis. cui-guard does not review logs. | The organization enables cui-guard audit logging, which records each forwarded or blocked request without recording the matched content, and retains the log under its own log management process. |
| 3.3.2 | 03.03.02 | Audit Record Content | Each record carries a session ID, the agent, lane and trust level, hit counts, the action taken, the IDs of blocking rules, a request hash, a policy hash and any override entries. Evidence: `src/cui_guard/audit.py`, `tests/security/` | Default audit fields. | Tying a session to a named person. Records identify sessions and policy, not people, so the customer relies on host and OS accounts for user attribution. | The organization configures cui-guard to record the decision fields for each request, and associates sessions with individual users through its host account controls. |
| 3.3.8 | 03.03.08 | Protection of Audit Information | Creates the log directory with mode 0700 and the log file with mode 0600. The log holds hashes and rule IDs, not content. | 3.13.1 | 03.13.01 | Boundary Protection | The gateway binds to 127.0.0.1 only, requires a per-session token, caps request bodies at 32 MiB, and refuses redirects. Evidence: `src/cui_guard/gateway/app.py`, `tests/pentest/`, `tests/security/` | Default bind and token settings. | Network boundary devices, host firewall and egress controls. The gateway is a software control on one host, not a network boundary. | The organization runs the cui-guard gateway on the loopback interface with a per-session token, as one layer of its boundary protection for AI agent traffic. |
| 3.13.8 | 03.13.08 | Transmission and Storage Confidentiality | Uses TLS 1.2 or later with certificate verification for every connection to the model endpoint. An absolute, owner-checked `ca_file` can pin the trust store. Evidence: `src/cui_guard/fips.py`, `tests/test_fips.py`, `docs/FIPS.md` | `ca_file` for organizations with their own CA bundle. | Protection of data at rest, and of everything other than the gateway's upstream connection. | The organization configures cui-guard to reach the model endpoint over TLS 1.2 or later using its approved CA bundle. |
| 3.13.11 | 03.13.11 | Cryptographic Protection | With `fips = "require"`, the gateway and launcher refuse to start unless four checks pass, so cryptography comes from the platform's FIPS 140-3 validated module. cui-guard is not itself a validated module. ## Limits of these statements

- A statement is a draft for the customer's own SSP. Nothing here says a requirement is satisfied.
- Several requirements, such as 3.1.3, depend on the customer's policy and on agents actually using the gateway.
- Rev 3 parameters are chosen by the organization, and DoD publishes its own selections. Check them before using the Rev 3 column.
